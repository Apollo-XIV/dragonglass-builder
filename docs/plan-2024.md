# Supporting the 2024 rules

A plan, not a commitment. The point of writing it now is that the 2024 rules stress the
schema in four specific places, and every one of them is cheaper to settle before there is
much content to migrate.

**On rules accuracy:** the rules summarised here are from memory and should be checked
against the books before any of it is converted. The *engineering* conclusions do not
depend on the fine detail — they depend on the shape of each rule, which is what the
sections below are really about.

`docs/schema.md` is the authority on the format. Anything this plan proposes is a proposal
until it lands there.

## What already works, with no engine change

Most of 2024 is a content exercise. These need converting, not building:

| 2024 rule | Why the schema already covers it |
| --- | --- |
| Species grant no ability bonuses | Removing modifiers from content. |
| Subclass at level 3 for every class | The subclass was always *a choice at a level*, never a schema concept. |
| Feat categories (Origin, General, Fighting Style, Epic Boon) | Tags on feats, plus `requires` for the level gate. An Epic Boon is `{ all: [{ type: "level", min: 19 }] }`. |
| Backgrounds grant an origin feat | A choice with `from: { kind: "feat", tags: ["origin-feat"] }`. |
| Feats that also give +1 to an ability | The ASI pattern: a nested `ability-point` choice. Already shipped. |
| Ability Score Improvement (+2 to one, or +1 to two) | Shipped: `count: 2, repeatable: true` over `ability-point`. |
| Shared Arcane/Divine/Primal spell lists | A spell list is already just a tag. |
| Weapon and armour training changes | Proficiency grants. |

The ability-point elements added for the ASI are reusable as-is: a 2024 background offers
**the three abilities it names** with `from: { ids: [...] }` and nothing else. Note that
`ids` is ANDed with every other criterion, so give it alone — adding a `kind` beside it
narrows rather than widens.

## What needs new vocabulary

Four gaps, in the order I would take them. The first is done; the rest are open, and only
gap 2 stands between here and converting a first slice of 2024 content.

### 1. A per-option cap on a repeatable choice — `maxPer` — **done**

**The rule.** A 2024 background gives +2 to one of its three abilities and +1 to another,
*or* +1 to each of the three.

**Why it doesn't fit.** Both shapes are "three points among these three abilities", which
is `count: 3, repeatable: true` — except nothing stops a player putting all three points
into one ability. The budget is expressible; the per-option ceiling is not.

**The vocabulary.** `maxPer?: number` on `ChoiceDef`: the most times any one option may be
taken. Meaningful only with `repeatable: true`; defaults to `count`.

```jsonc
{ "id": "srd24:background:acolyte:abilities", "count": 3, "repeatable": true, "maxPer": 2,
  "from": { "ids": ["srd24:ability-point:int", "srd24:ability-point:wis",
                    "srd24:ability-point:cha"] } }
```

**Shipped.** `maxPer` on `ChoiceDef`, documented in `docs/schema.md`; validated as a
number ≥ 1, with a warning when it is set without `repeatable`; bounded in the picker's
`cycle`, so a tap with no room clears the option rather than overspending; and reported by
the resolver when a stored answer exceeds it — the excess picks land in `invalid`, the
character carries a `choice-invalid` diagnostic, and the choice reads as incomplete. A
hand-edited file is told what is wrong rather than quietly obeyed or quietly rewritten.

It also retro-fits the 2014 ASI's unstated rule — two points may go in one ability but
never three — which was previously only true because `count` happened to be 2.

### 2. Character-level progression outside a class — **done**

**The rule.** 2024 species features arrive at character levels, not all at level 1 —
Dragonborn flight, Aasimar revelations and so on. **[Decided]** that this is supported:
there is no other sense in which a character progresses outside a class, and a species
that gains something at level 5 is exactly the case.

To be clear about what this is *not*: nothing progresses on its own clock. Every level a
character has is still a class level in `build.levels`, and total character level is just
how many of those there are. What is missing is only the ability for a **non-class element**
to key its parts against that total.

**Why it doesn't fit.** `levels` is honoured only for an element governed by a class.
`collect.ts` reads it under `if (el.levels && el.kind !== "class" && ctx.class)`, so a
species with a `levels` map is **silently ignored** — verified: a trait declared at level 5
of a species never appears, with no diagnostic. That silence is the worst part; a converter
would write it and never find out.

**Proposal, and a decision to make.** The same `levels` field cannot mean class level in
one place and character level in another without a discriminator. Two options:

- `levelsBy: "class" | "character"` on the element, defaulting to `class` for classes and
  subclasses and `character` for everything else. Explicit, and it reads well in content.
- Infer it: an element with no governing class is read against character level. Less to
  write, but it makes the meaning of a field depend on where it was reached from, which is
  exactly the kind of thing this schema has otherwise avoided.

I prefer the explicit field. Either way the first fix is the smaller one: **report a
diagnostic when an element declares `levels` that nothing will ever read**, so the current
silence stops being silent even before the feature lands.

**Cost.** Moderate. A second walk in `collect`, driven by total level rather than class
level, plus a decision about what happens to the picks when total level changes (the class
machinery in `levels.ts` has no say here). Worth doing properly rather than quickly.

### 3. Modifiers aimed at something the player named

**The rule.** Weapon mastery: you choose N weapons, and the mastery property of *those*
weapons becomes available to you. Also the general family — "choose a damage type", "choose
a skill" — of which 2024 has more than 2014.

**Why it doesn't fit.** Choosing the weapons is fine: they are items, so
`from: { kind: "item", tags: ["weapon"] }` with a `count` works today. What does not fit is
a modifier that applies *to the thing chosen*: `Modifier.target` is a literal stat path,
and nothing substitutes an answer into it.

**Why the ASI escaped this and mastery doesn't.** The ASI works because two things are
true of abilities and not of weapons: there are exactly six of them, so one element each
is reasonable; and an ability score **is a stat path**, so each element can carry a
concrete modifier. Neither holds for mastery. There are dozens of weapons, and more
importantly there is no stat path meaning "how the longsword's attack resolves" —
Graze deals damage on a miss, Vex grants advantage on the next attack. Those are rules
about attack resolution, which the engine does not model at all. So this is not one gap
but two: no parametrised targets, *and* nothing numeric to point them at.

**Which reframes the fix.** The link worth building is not a modifier at all. The answers
to "choose three weapons" are item ids, and `resolver/attacks.ts` already joins equipped
items to attack rows. It could join *chosen* items to those same rows, generically: a
choice whose options are items, whose answers annotate the attacks built from those items.
No templating language, no new modifier vocabulary — the mastery's text appears on the
longsword's row because the player named the longsword.

That is a resolver and display feature rather than a schema change, which is the strongest
argument that the templating idea was the wrong tree. It needs a second real case before
the generic shape is clear, so the recommendation stands: **defer**, and in the meantime
convert the masteries as elements the choice grants, with their text attached as a
situational annotation (`when: { text: "with a weapon you have mastery with" }`). That is
the schema working as designed — attributed, visible in the breakdown, never folded into a
number — and honest that the engine is not tracking which weapon.

### 4. The ceiling of 20 — **done**

**The rule.** Increases can't take a score above 20.

**Why it's awkward.** It is not a global ceiling — magic items legitimately exceed 20 — so
`{ op: "max", value: 20 }` on `abilities.*.score` would be wrong. The 5e rule is
per-source: *this feature* can't take you above 20.

**What exists already.** An ability-point element can carry its own prerequisite:

```jsonc
{ "id": "srd24:ability-point:str", "kind": "ability-point",
  "requires": { "not": [{ "type": "ability", "ability": "str", "min": 20 }] } }
```

That needs no new vocabulary, and with enforcement off it warns rather than hides, which is
this project's house style. **But** `abilityScore` in the requirement context reads the
*resolved* score, which already includes the points taken — so the option that brought you
to 20 then reads as unmet. The pick is not removed (requirements only warn or hide), so it
degrades acceptably, but the boundary is off by one and someone will notice.

**Done.** The ceiling is a **soft limit in the builder**, not a rule the engine enforces. Going over 20 is allowed if the player confirms it, through the same kind of
confirmation sheet that removing a level uses. Nobody is blocked from building the
character they want, and a table playing with a houseruled cap is not fighting the tool.

That decision dissolves the hard part. The resolver does not need to re-phase its
requirement context, because the check moves to the moment of the pick: on commit, if an
answer would take a score above 20, ask. The `requires` approach above is then unnecessary
and should not be added to content — one mechanism for this, in the builder, where the
player is.

**Shipped** as `softMax` on the `stat-path` element — so the cap is content, not code, and a
table that houserules it moves one number in one file. `src/core/resolver/caps.ts` reports
breaches purely; `useBuildChange` resolves the prospective build and folds any new breach
into the *same* confirmation sheet as the invalidation report, because two confirmations for
one tap is how a builder teaches people to stop reading them. A character already over a cap
is not asked again, and the resolver never clamps: a score of 23 reports as 23.

## Remaining snags, found while implementing the above

Three things surfaced that were not in the original four. None blocks a conversion; all
three are worth knowing before one starts.

**Expertise turns out to be free.** I had half-expected it to need the same treatment as
mastery. It does not: a skill element already carries its own
`{ target: "skills.athletics", op: "proficiency", value: "proficient" }` — there is no
convention in the engine, it is all data — so an expertise element is the same thing with
`value: "expertise"` and a `requires` of
`{ all: [{ type: "proficiency", proficiency: "athletics" }] }`. Eighteen elements, reusable
by Rogue, Bard and anything else, no new vocabulary. The same pattern covers "choose a
damage type" (one element per type) and any other enumerable outcome that *is* a stat path.

**Conditions apply nothing.** `state.5e` records which conditions are active and the
resolver passes them through, but no condition contributes modifiers, and there are **zero
`condition` elements in any source**. In 2014 that mattered less, because most conditions
are adjudicated at the table. 2024 makes exhaustion a scaling numeric penalty — −2 per level
to d20 tests — which is exactly the kind of thing a sheet should apply and currently cannot.

Two parts to it. The mechanism is nearly there: `effects` are already "a named, toggleable
overlay of modifiers" driven by live state, so a condition wants the same treatment. What is
genuinely missing is an expression reference to a condition's own stack count — something
like `@exhaustion` — so one element can say −2 × level rather than six near-identical
elements saying −2, −4, −6. Note also that `saves.all`, `checks.all`, `skills.all` and
`abilities.all.score` fan out to their families, but **`attacks.all` does not**, so a
penalty to every d20 test cannot currently reach attack rolls in one modifier.

**Weapon mastery, resolved.** The conclusion from the discussion above: 2024 weapons carry
their mastery property as part of the item, as text in the item's details. That works today
and needs nothing. What it does *not* do is tell the sheet that *this character* has mastery
with *this* weapon — the mastery reads as a property of the longsword rather than of the
character's relationship to it. The choice of which weapons is still a perfectly ordinary
choice over item elements, so the data is all there; only the display join is missing, and
it is a display feature rather than a schema one. Good enough to convert against.

## Two editions in one vault

Worth settling early because it shapes ids. A 2014 and a 2024 source can coexist today:
ids are namespaced by source, so `srd:class:paladin` and `srd24:class:paladin` are
different elements, and a character's own `sources.5e` already overrides the vault-wide
list.

What is missing is only ergonomics. A character that loads both will be offered both
Paladins, with nothing to say which is which beyond the source badge. The cheap fix is a
`ruleset` field on the `sourcebook` element (`"2014"` | `"2024"` | anything a homebrewer
likes), used for grouping and labelling, plus a per-character default. That is a smaller
problem than it looks and does not need solving before conversion starts — but ids should
be namespaced with the edition from the first file, because renaming them later means
rewriting every character that referenced them.

## Suggested order

1. ~~**`maxPer`**~~ — done.
2. ~~**Character-level progression**~~ — done: `levelsBy: "character"`, with the staged
   features shown on the level card that brought them and looked ahead to in Planned.
3. ~~**The soft ceiling**~~ — done: `softMax` on a stat path, confirmed in the builder.
4. **Convert one vertical slice** of 2024 content: one background, one species with no
   ability bonuses, one origin feat, one class to level 5. Add it to
   `tests/srd/` with the numbers written out longhand, the way the 2014 slice is. This is what turns the rest of this document from speculation into a list.
5. **Mastery** (gap 3) — last, and only once a second case shows what the generic shape is.

Nothing in the schema now blocks a 2024 conversion. What remains are the snags below, all
of which are either content decisions or things a first slice will surface properly.

The slice at step 3 is the important one. Every gap listed here was found by reading the
schema against the rules; the ones worth building are the ones a real conversion trips
over.
